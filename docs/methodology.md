# 评测体系（用户视角）

一个准备用大模型网关/中转 API 的用户，真正关心的问题只有五个。每个问题对应一个评测维度、
一组可自动化采集的指标。所有指标都来自公开可复现的拨测脚本（`probe/probe.mjs`），
原始数据全部提交在 `data/results/`。

## 维度一：直连性 —— "我能不能直接连上？"

| 指标 | 采集方式 |
|---|---|
| 可达性 | `GET /v1/models` 是否 2xx |
| 连接延迟 | 上述请求的端到端耗时（按探测地域分列） |
| 地域覆盖 | 同一探测从多个地域跑（GH Actions 美国 / 后续：国内自托管 runner、香港、新加坡边缘探针） |

> 国内直连是中文用户的第一关心点，也是现有所有评测站都不覆盖的点。v1 先有美国视角，
> 地域矩阵是第一优先级的 roadmap 项。

## 维度二：稳定性 —— "它会不会半夜挂掉？"

| 指标 | 采集方式 |
|---|---|
| 成功率（uptime%） | 每 6 小时拨测的请求成功率，按天聚合、按 7/30 天滚动 |
| 错误画像 | 失败请求的 HTTP 状态/错误类型分布（429 限流 vs 5xx 故障 vs 超时） |
| 延迟漂移 | TTFT p50 的 over-time 曲线，识别"高峰期变慢" |

> 这是数据积累的长线价值所在：跑得越久，曲线越有说服力，新站点抄不走。

## 维度三：速度 —— "它快不快？"

| 指标 | 定义 |
|---|---|
| TTFT | 发起流式请求到收到第一个内容 token 的耗时，报 p50/p95 |
| 吞吐 tok/s | 首 token 之后的生成速率（completion_tokens ÷ 生成耗时） |
| 端到端耗时 | 整个请求完成时间 p95 |

方法论沿用 llmperf 社区惯例：固定小 prompt、限定 max_tokens、单次拨测多采样取分位数、
并发 ≤4 避免变成压测。探测 prompt 公开在脚本里。

## 维度四：价格 —— "它贵不贵？有没有套路？"

| 指标 | 采集方式 |
|---|---|
| 标价 $/1M tokens（输入/输出） | 网关公开价格接口或价格页；官方价取 litellm 开放价格库 |
| 价格指数 | 同一模型网关价 ÷ 官方价的均值（<1 便宜，>1 贵） |
| 计费透明度 | 是否有公开价格 API、是否区分缓存价、是否有隐藏倍率（人工标注） |

## 维度五：模型清单 —— "我要的模型它有没有？"

| 指标 | 采集方式 |
|---|---|
| 模型数量 | `GET /v1/models` 返回数 |
| 关键模型覆盖 | 主流模型（Claude/GPT/Gemini/DeepSeek/Qwen 旗舰与 flash 档）的可用矩阵 |
| 协议覆盖 | OpenAI 兼容 / Anthropic 原生 / Gemini 原生 |

## 远期维度六：保真度 —— "它给我的真是这个模型吗？"

参考 [K2 Vendor Verifier](https://github.com/MoonshotAI/K2-Vendor-Verifier) 的方法：
固定请求集合（含工具调用）回放到网关与官方 API，对拍工具调用合法率、输出分布差异，
检测偷换模型、过度量化、截断上下文。这是中转网关评测真正的"杀手维度"，列入 roadmap。

## 综合评分

v1 不做加权总分（容易被质疑黑箱），排行榜默认按"稳定性 30 天 uptime"排序，
其余维度各自独立成列，用户按自己关心的列排序。

## 公正性声明

- 拨测代码、原始数据、聚合逻辑全部开源，任何人可用自己的 key 复现；
- 网关清单接受 PR 自助提交（`data/gateways.json`）；
- 维护者与其中某网关存在利益关联时在清单条目中披露。
